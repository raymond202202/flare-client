# flare 客户端「原生技术重写」调研报告 · 方案设计 · 执行计划

> 调研日期：2026-10-29
> 决策背景：Qt 精简路线（macOS 已做到 .app 98.3 MB → 35 MB，GUI pkg 14.8 MB）已被否决，Windows / macOS 改用**各自平台原生技术**重写 GUI 客户端。
> 调研方法：**不靠纸面选型**。先在两台真机上各写一个「能跑的最小壳子」（spike），用系统自带工具链编译、启动、量体积，拿实测数字再下结论。
> 环境：macOS 26.5.2 / arm64（macmini，Swift 6 工具链、`swiftc` 可用）；Windows 11 x64（`goodwork` 机，.NET Framework 4.8 in-box、`csc.exe` 可用）；Linux Fedora 44 KDE Wayland。

---

## 一、结论先说（TL;DR）

| 项 | 结论 |
|---|---|
| **推荐方案** | **Windows 用 WPF（.NET Framework 4.8，系统自带）** + **macOS 用 SwiftUI（系统框架）**，两端都是「**薄壳**」：只管画界面 + 起引擎进程，所有智能都在 Go 引擎里 |
| **实测体积（壳本身）** | Windows：`FlareSpike.exe` **7,680 字节**，zip 后 3,528 字节；macOS：二进制 **144,200 字节**，`.app` **168 KB**，`.pkg` **52,581 字节** |
| **运行时依赖** | **零**。Windows 侧 WPF 程序集全在 GAC（系统自带）；macOS 侧依赖全是 `/System/Library/Frameworks` + `/usr/lib/swift`（系统自带） |
| **预测交付包体积** | Windows GUI 包：**21.9 MB → ≈4.3 MB**（−80%）；macOS GUI 包：**14.8 MB → ≈4.7 MB**（−68%） |
| **工作量** | 现有 Qt 客户端代码量实测 **2,512 行**（`src/` 2,131 + `engine-bridge/` 381，18 个源文件），不是旧评估文档写的「2 万行量级」——**那个数字是错的，重写成本被高估了** |
| **引擎** | Go 引擎**已经是平台中立的**，三平台同源同一份协议，原生壳直接复用，**不需要改引擎**（只需给更新检查换个仓库指向） |
| **Linux** | **不动**。仍是「Go 引擎 RPM + 系统 Qt GUI RPM」，两个包各 ≈3.8 MB，已经是全平台最瘦 |
| **最大风险** | 不是体积也不是工具链，而是 ①**中文输入法（IME）**在两端原生控件里的表现；②**macOS 无签名/公证的 Gatekeeper 拦截**；③**Markdown + 代码高亮的渲染保真度**。这三项都在 M1 用 spike 先验证，验不过就止损 |

**一句话**：重写壳是**净赚**的买卖——两端壳合计 ≈220 KB 原生代码换来 17 MB（Windows）/ 10 MB（macOS）包体下降，而且顺带干掉「打包 Qt」这一整个长期维护负担（不用再维护精简 Qt 编译脚本、不用再追 Qt 版本、不用再解 ICU/DLL 闭包）。

| 痛点 | 现状 |

## 三、Windows 侧候选技术评估

### 3.1 候选对比

| 方案 | 壳体积增量 | 运行时依赖 | 工具链 | Markdown/高亮 | 判定 |
|---|---|---|---|---|---|
| **WPF（.NET Framework 4.8）** | **≈0**（程序集系统自带）+ 库 ≈0.7 MB | **零**（Win10 1903+/Win11 全部 in-box 4.8） | **系统自带 `csc.exe` 就够**（本次实测），无需 .NET SDK / VS | Markdig + ColorCode（NuGet，实测可下） | ✅ **推荐** |
| WinUI 3 + Windows App SDK | ≈15–25 MB（自带 WASDK 运行时，不装就闪退） | 需 WASDK 运行时或 self-contained | 需 .NET 8 SDK + VS/MSBuild + Windows SDK | CommunityToolkit | ❌ 与「减重」目标背道而驰 |
| Win32 + C++ / Direct2D | 最小（几百 KB） | 零（系统 DLL） | 需 MSVC + Windows SDK | **全部手写**（文本布局/滚动/命中测试都得自己来） | ❌ 工作量爆炸（相当于重写一个文本控件库） |
| WebView2 壳（复用现有 Web 前端） | ≈1 MB | 依赖 Edge WebView2 运行时（Win11 自带，Win10 需装） | 简单 | 现成 | ❌ 不算「原生技术」；且本仓没有可复用的 Web 前端 |
| .NET 8 self-contained WPF | ≈60–70 MB | 零 | 需 .NET 8 SDK | 同上 | ❌ 包体爆炸 |

**选 WPF/.NET Framework 4.8 的核心理由**：这是**唯一能同时满足「零运行时依赖」+「零 SDK 安装」+「系统原生渲染」**的组合。用户机器上什么都不用装，我们的 CI 也不用装 SDK —— 本次 spike 就是拿 `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe` 直接编出来的。

### 3.2 .NET Framework 4.8 的兼容性边界（必须诚实说明）

- Windows 10 1903+ / Windows 11：**内置 4.8**，无需下载。
- Windows 8.1 / 7：需装 .NET Framework 4.8 运行时（≈60 MB 一次性）。**声明最低支持 Windows 10 1903**即可规避。
- 缺失时的兜底：安装包 `installer.nsi` 里加一段检测（读注册表 `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full\Release` ≥ 528040），不满足就提示下载链接而不是装完闪退。

### 3.3 Markdown + 代码高亮的库选型（NuGet 实测可达）

| 库 | 版本（实测最新） | 体积（net462/netstandard2.0） | 用途 |
|---|---|---|---|
| `Markdig` | 1.5.1 | `Markdig.dll` **518,144 B** | CommonMark + GFM 解析（表格、任务列表、删除线） |
| `ColorCode.Core` | 2.0.15 | `ColorCode.Core.dll` **122,000 B** | 代码高亮（自带 C#/JS/Python/JSON/Bash 等定义） |
| `Markdig.Wpf` | 0.5.0.1 | `Markdig.Wpf.dll` **37,376 B** | Markdig AST → WPF `FlowDocument` 现成渲染器 |

三条路：①直接用 `Markdig.Wpf`（省事，但样式定制受限）；②Markdig 解析 + **自写 AST → `FlowDocument` 渲染器**（≈400 行，样式完全可控，能精确复刻浅白紫）；③全手写 Markdown 解析（不推荐）。
**建议 ②**：Markdig 只当解析器，渲染自己写 —— 这样两端（macOS 也用 swift-markdown 拿 AST）可以共享同一份「样式规格」，视觉一致性可控。

## 四、macOS 侧候选技术评估

### 4.1 候选对比

| 方案 | 壳体积 | 运行时依赖 | 工具链 | 判定 |
|---|---|---|---|---|
| **SwiftUI** | 二进制 **144,200 B** / `.app` **168 KB** / `.pkg` **52,581 B**（实测） | 零（`/usr/lib/swift` 系统自带，macOS 12.3+） | 命令行 `swiftc` 即可（本次实测），Xcode 可选 | ✅ **推荐** |
| AppKit（Cocoa） | 与 SwiftUI 同量级 | 零 | `swiftc` / ObjC | ✅ 备选（SwiftUI 做不了的地方下沉到 AppKit：`NSTextField` 富文本、`NSVisualEffectView`） |
| WKWebView 壳 | ≈1 MB + 前端资源 | 零 | 简单 | ❌ 不算原生 |

**结论：SwiftUI 为主，必要处下沉 AppKit**。macOS 上 SwiftUI/AppKit 混用是官方支持的常规做法（`NSViewRepresentable`）。

### 4.2 语言与解析库

| 库 | 实测可达 | 说明 |
|---|---|---|
| `apple/swift-markdown` | ✅（`git ls-remote` 通） | 官方 CommonMark 解析器，SPM 依赖，静态链进壳 |
| `johnxnguyen/Down` | ✅ | cmark 封装，输出 `NSAttributedString` 现成 |
| `raspu/Highlightr` | ✅ | 高亮，但**内嵌 highlight.js 资源 ≈1–2 MB** → 体积敏感，需裁剪语言包或改用自研分词器 |

**建议**：`swift-markdown` 取 AST + 自写 `AttributedString` 渲染器；代码高亮**自研轻量分词器**（只覆盖我们实际会遇到的 8–12 种语言，≈300 行），避免为了高亮塞进 2 MB JS 运行时。

### 4.3 macOS 分发的硬约束（必须提前告诉用户）

- **无 Apple Developer 账号（99 美元/年）→ 无法公证（notarize）**。内测期现实做法：
  - 现状（Qt 版）用 ad-hoc 签名（`codesign --sign -`）可以安装，但用户首次打开会遇 Gatekeeper 提示；
  - **`.pkg` 走 `sudo installer -pkg` 命令行安装可绕过 Gatekeeper 的文件隔离提示**（现有验收脚本就是这么装的）；
  - 与现状相比**没有变差**：Qt 版的 `codesign --verify` 也是 ad-hoc。原生版沿用同一策略。
- 若以后要正式发布，再评估开发者账号。

## 六、体积预测（基于实测的算术，不是猜）

壳 = 原生代码 + Markdown/高亮库；GUI 包 = 壳 + Go 引擎（压缩后）。

| 组成 | Windows | macOS |
|---|---|---|
| Go 引擎（原生二进制，未压缩） | 11,256,832 B | ≈10 MB |
| Go 引擎（NSIS/pkg 内压缩后） | **3,987,120 B**（现有引擎包实测） | **4,503,960 B**（现有引擎包实测） |
| 原生壳 exe/二进制 | 7,680 B | 144,200 B |
| Markdown 解析 + 高亮库 | ≈0.7 MB（Markdig 518 KB + ColorCode 122 KB） | ≈0.4–0.8 MB（swift-markdown + 自研高亮，静态链） |
| 图标 / 资源 / 字体（仅中文 UI 字体不打包，用系统） | ≈0.1 MB | ≈0.1 MB |
| 安装包框架开销 | ≈0.05 MB（NSIS） | ≈0.05 MB |
| **GUI 包预测** | **≈4.3–4.6 MB** | **≈4.7–5.2 MB** |
| **对比现状** | 21,862,126 B（−80%） | 14,802,402 B（−68%） |

> 结论：**两个平台 GUI 包都会落到 5 MB 以内**，与纯引擎包（≈4 MB）同量级。这意味着以后**"GUI 包内置引擎"带来的体积惩罚基本消失**，「双包制」对用户的认知负担也可以进一步简化（用户只需下一个包）。

## 八、与 Go 引擎的集成设计（两端同一套）

### 8.1 现状（可直接复用）

`engine-bridge/engine_bridge.cpp`（381 行）已经定义了协议：起子进程 → stdin 写 JSON 帧 → stdout 读 JSON 行帧 → 分发事件。原生壳只是把这段**翻译成各平台原生进程 API**，协议本身一个字都不用改。

### 8.2 进程定位（沿用现有双包制路径）

| 平台 | 引擎查找顺序 |
|---|---|
| Windows | ①GUI 同目录 `flare.exe`（GUI 包内置）②`%LOCALAPPDATA%\Programs\flare\flare.exe`（独立引擎包）③`PATH` |
| macOS | ①`Flare Client.app/Contents/MacOS/flare`（内置）②`/usr/local/bin/flare`（引擎包）③`PATH` |

### 8.3 帧协议（保持 JSON Lines，逐行 `\n` 分隔）

请求（stdin）：`{"id":..,"type":"chat","session":..,"text":..}`；事件（stdout）：`{"type":"chunk"/"tool"/"confirm"/"done"/"error",...}`；确认回传（stdin）：`{"type":"confirm","id":..,"decision":"allow_once|deny"}`。

> 关键点：**先 `sessions` 握手帧，再 `chat`**（现有 Qt 版即如此）；Windows 没有 SIGTERM，停止用 `stop` 帧 + 超时后 `TerminateProcess`；macOS 用 `terminate()` 兜底。

### 8.4 顺手修的一个真 bug（本次调查发现）

`flare-client/src/versionpanel.cpp:13-14`：

```cpp
const char *kGuiRepo    = "raymond202202/flare-client";  // GUI 自身更新
const char *kKernelRepo = "raymond202202/flare";         // ← 引擎更新比对的是 Node 版仓库
```

**（历史问题，已于 2026-10 随仓库改名修复）** 此前引擎检查更新比对 `raymond202202/flare`（当时是 Node 版），而 Go 引擎实际发在 `flare-go`，用户点「检查引擎更新」会拿到 Node 版的版本号。

**现已彻底修复**：`flare-go` → `flare`（Go 引擎成为主线），原 Node 版 `flare` → `flare-node`。因此 `src/versionpanel.cpp:14` 的 `kKernelRepo = "raymond202202/flare"` **无需改代码**就已经指向 Go 主线；实测 `api.github.com/repos/raymond202202/flare/releases/latest` 返回 `v0.6.163`（Go 引擎发布）。

## 十、方案设计（要落地的东西）

### 10.1 目录结构（放 `flare-client` 仓，`src/` 原封不动）

```
flare-client/
├── src/              # 现有 Linux Qt 客户端（不动）
├── engine-bridge/    # 现有 C++ 桥（不动，仅作协议参考实现）
├── native/
│   ├── protocol/     # 三端共享：协议文档 + 黄金测试语料（JSONL 帧样本 + 期望渲染）
│   ├── windows/      # WPF/C# 客户端：FlareClient.csproj（csc 直编脚本）+ ui/ + md/ + engine/
│   └── macos/        # SwiftUI 客户端：Package.swift + Sources/{App,UI,Markdown,Engine}/
├── packaging/{windows,macos}/   # 新增原生打包脚本（与 Qt 版并存）
└── docs/            # 本文档 + 协议说明
```

### 10.2 共享「薄壳」原则（两端必须一致）

1. **智能全在引擎**：壳不发 LLM 请求、不解析工具协议、不做上下文裁剪 —— 只转发和渲染。
2. **渲染规格单一来源**：`native/protocol/render-spec.md` 定义颜色/字号/间距/圆角/动效曲线，两端按同一份表实现对（保证视觉一致，也避免"改一处两端不同步"）。
3. **UI 状态机同构**：`Idle → Streaming → AwaitingConfirm → Idle`，两端同名同义，测试用例共享（`native/protocol/golden/*.jsonl`）。
4. **主题**：浅白紫，主色 `#6d4aff`，禁用深色模式；系统深色模式下也保持浅色（与现有 Qt 版一致）。

### 10.3 关键技术选型汇总

| 关注点 | Windows | macOS |
|---|---|---|
| UI 框架 | WPF（.NET Framework 4.8） | SwiftUI（12.3+），必要时 AppKit 下沉 |
| 语言 | C# 5.0（csc 自带版本上限，够用） | Swift 6 |
| Markdown | Markdig 解析 + 自写 FlowDocument 渲染 | swift-markdown 解析 + 自写 AttributedString 渲染 |
| 高亮 | ColorCode.Core | 自研轻量分词器 |
| 进程 | `System.Diagnostics.Process` | `Process`（Foundation） |
| HTTP（更新检查） | `HttpClient`（.NET FW 4.8 有） | `URLSession` |
| 存储（窗口状态/设置） | `%APPDATA%\flare-client\*.json` | `UserDefaults` + `~/Library/Application Support/Flare` |
| 构建 | `csc.exe`（系统自带）+ 打包脚本 | `swiftc` / `swift build`（SPM 静态链）（系统自带） |
| CI | GitHub Actions `windows-latest`（公开仓免费） | `macos-latest`（免费额度） |

## 十一、执行计划（M0–M6，每步有验收门禁）

> 原则：**每一步都能独立交付并回滚**；不通过门禁不进下一步（止损点写死在每个里程碑）。

| 里程碑 | 内容 | 验收门禁 | 预估 |
|---|---|---|---|
| **M0 协议与语料固化** | 从 `engine-bridge` + Qt 版抽出协议文档；生成黄金帧语料（会话、流式、工具卡、确认、错误、中文长文本）；写 `render-spec.md` | 语料可被现有 Qt 版跑通并截图存档（作为视觉基准） | 1 轮 |
| **M1 高风险 spike（两端各一）** | ①WPF：Markdig→FlowDocument 渲染 + 流式追加 1 万字不掉帧 + IME 中文输入；②SwiftUI：swift-markdown 渲染 + 流式 + `NSTextView` IME 回退 + `.pkg` 体积实测 | **渲染保真度**（与 M0 截图逐项比对）、**流式不卡**、**中文输入正常**、包体 ≤6 MB。**任一项失败 → 停下来找替代方案（详见风险表）** | 1–2 轮 |
| **M2 Windows 完整壳** | 18 项功能全实现 + 引擎进程管理 + 更新检查（指向 `flare`）+ 双包制 NSIS | 真机：双击向导装/`/S` 装/命令行装；与引擎包共存；完整对话一屏跑通；卸载干净 | 2–3 轮 |
| **M3 macOS 完整壳** | 同上（SwiftUI）+ universal 二进制 + `productbuild` | macmini 真机：`installer` 装、`/Applications` 启动、对话跑通、`codesign --verify` 通过、包体实测 | 1–2 轮 |
| **M4 视觉与动效对齐** | 按 `render-spec.md` 逐条对齐 Qt 版（气泡/间距/圆角/spring/面板联动/欢迎页） | 与 M0 基准截图并排比对（像素级差异列表逐条裁决） | 1–2 轮 |
| **M5 更新与发布流水线** | 三端更新检查统一（引擎→`flare`，GUI→`flare-client`）；GitHub Releases + 打包脚本进 CI；飞书文档更新 | 点"检查更新"能正确识别新版本；CI 能出三端包 | 1 轮 |
| **M6 内测分发** | 六包（或四包，若 GUI 内置引擎后只发 GUI 包）上传飞书 + 安装说明文档；脱敏复扫 | 用户凭链接可下载安装；包体在 20 MiB 内；文档含双击/命令行两种装法 | 1 轮 |

**总预算**：约 8–12 轮交互式工作。**止损点**：
- M1 若 Markdown 保真度或 IME 任一失败且无替代 → 回退到「Qt + 自建精简 Qt（macOS 已做到 35 MB）」，并把 Windows 侧改成 `-no-icu` 自建 Qt（≈40 MB）；
- M2/M3 若某平台阻塞超过 3 轮 → 该平台保留 Qt 版，另一平台先上原生（**允许不对称交付**）。

## 十二、风险登记册

| # | 风险 | 影响 | 概率 | 缓解 / 止损 |
|---|---|---|---|---|
| 1 | **Markdown + 高亮保真度**在原生控件里做不好（表格、嵌套列表、长代码块换行） | 观感退化，用户不可接受 | 中 | M1 先做渲染 spike 并与 Qt 截图逐项比对；备选：`Markdig.Wpf` 现成渲染器；macOS 用 `Down`+`NSAttributedString` |
| 2 | **中文输入法（IME）**：SwiftUI `TextEditor` 在 macOS 上有候选词定位/组合态问题 | 打不了中文 = 不可用 | 中 | M1 实测；不达标就下沉 `NSTextView`（可靠但要多写 ≈200 行） |
| 3 | **流式追加性能**：WPF 每次追加重建 `FlowDocument` 会卡 | 长回答卡顿 | 中 | 分批刷新（≥60ms 合并）+ 只追加不重建 + 虚拟化；M1 用 1 万字压测 |
| 4 | **长期三套 UI 代码**（Linux Qt + Win + mac） | 维护成本 | **高（确定性）** | 用「薄壳 + 共享协议语料 + 共享 render-spec」把壳做到最薄；若日后 Linux 也要原生，再评估 GTK4 |
| 5 | macOS 无公证 → Gatekeeper 提示 | 用户装不上 | 中 | 文档给 `sudo installer -pkg`；与现状一致，不算退化 |
| 6 | Windows 老系统无 .NET 4.8 | 双击闪退 | 低 | 安装器检测注册表，缺则引导安装；声明最低 Win10 1903 |
| 7 | 动效（spring 曲线）在 WPF 里做不出完全等价 | 观感差一点 | 中 | WPF 手写 spring 解析解（临界阻尼公式，≈60 行）；或退化为 `QuinticEase`，M4 时裁决 |
| 8 | 体积预测偏差（Markdig 等库比预期大） | 包体超 20 MiB | 低 | 库是百 KB 级、引擎压缩 4 MB 级，离 20 MiB 很远；实测在 M2 收口 |
| 9 | 协议变更导致三端不同步 | 行为分叉 | 中 | `native/protocol/golden/` 语料是三端共同门禁，任何协议改动必须过三端 |

## 十三、结论与建议

1. **技术上可行，且成本远低于旧评估**。旧文档说「2 万行 Qt 应用重写成本太高」，实测 Qt 客户端只有 **2,512 行**、且无图片附件/无语法高亮 —— 重写范围是清晰可控的。
2. **收益明确**：Windows GUI 包 21.9 MB → ≈4.3 MB，macOS 14.8 MB → ≈4.7 MB，**分发障碍（飞书 20 MiB）彻底消失**，并可彻底退役「打包 Qt / 裁 ICU / 解 PE 闭包」这一整套维护链。
3. **风险集中在三处**（Markdown 保真、IME、流式性能），全部可以在 M1 用一周内的 spike 验证完，**验不过就止损回退**，不会出现"做到一半发现不行"。
4. **引擎不动**：Go 引擎已是平台中立的成品，原生壳直接复用；原先「检查更新比对错仓库」的 bug **已随 2026-10 仓库改名自动修复**（详见 8.4、9.4），原生壳只需沿用 `raymond202202/flare` 这一指向。
5. **建议 M0 立刻可开工**（纯文档与语料，零风险、零破坏性），M1 结论出来后再决定是否全力推进 M2–M6。
